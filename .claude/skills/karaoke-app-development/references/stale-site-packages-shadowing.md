# Python Stale `site-packages` Shadowing Editable Installs

## The Problem
When running `pip install -e .` (or `make install`) inside a Python project, if a previous non-editable manual copy of the package remains inside the environment's `site-packages/` directory, Python's import system will silently prioritize the files inside `site-packages/` over the symlink or PEP-660 editable wrappers. Any changes you make to the local workspace codebase are completely ignored during execution, leading to extremely frustrating debugging sessions.

Additionally, `pip uninstall` might successfully claim to uninstall the package, but will leave behind the static copy in `site-packages/` if it wasn't originally registered with a pip `RECORD` (e.g. if it was manually copied or installed by a custom script).

## The Diagnosis
To confirm if you are suffering from stale `site-packages` shadowing:
1. Run a quick check using your project's python interpreter:
   ```bash
   python -c "import <package_name>; print(<package_name>.__file__)"
   ```
2. If the printed path is inside `site-packages/` (e.g., `.venv/lib/python3.14/site-packages/<package_name>/__init__.py`) instead of pointing to your local repository workspace (e.g., `/home/tina/karaoke/src/<package_name>/__init__.py`), your editable installation is being shadowed.

## The Resolution
1. Run pip uninstall:
   ```bash
   pip uninstall -y <package_name>
   ```
2. Manually delete the stale static directory inside `site-packages/`:
   ```bash
   rm -rf <venv_path>/lib/python<version>/site-packages/<package_name>
   ```
3. Re-install in editable mode:
   ```bash
   pip install -e .
   ```
4. Verify again that the printed package file path now points directly to your workspace.
